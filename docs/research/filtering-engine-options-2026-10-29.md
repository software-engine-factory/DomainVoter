# Filtering engine options for the local preview

The next comparison should test optimized SQLite against PostgreSQL on the same local data and CPU, RAM and disk budget. A search service is a third candidate only if those two miss the filtering targets. Changing engines alone will not remove broad exact counts, seed-dependent sorts or redundant round copies.

These are design recommendations, not measured speedups. This investigation read application code, saved local evidence and official documentation. It ran no benchmarks, migrations, services or production requests.

## What the local evidence establishes

The October 29 backup contains 2,468,782 pool names, including 2,338,250 five-character names. The integrated preview created 800,000 names across 80 rounds in 537.65 seconds. Its first cold batch page spent 38.1 seconds computing aggregates, followed by a 159 ms warm request. These are individual development-server observations, not production measurements or a controlled engine comparison. See [preview evidence](performance-2026-10-29-preview.md).

The code already has length, availability, price and partial set indexes, cached counts and reader workers. That does not prove that a combined filter plus its requested ordering uses a useful index. `poolWhere` combines flags, provider, class, evidence, price and availability. `countBlock` counts all matches before applying its cap. `orderSql` computes `dv_seeded_rank(seed,name)` for seeded ordering. `openBatchRound` inserts full domain rows from frozen batch names. See `src/lib/pool.ts`, `src/lib/batches.ts`, `src/db/migrations.ts` and `src/lib/creation-worker.cjs`.

## Engine comparison

| Candidate | Useful capability | Limitation for this workload | Recommendation, unmeasured |
| --- | --- | --- | --- |
| Optimized SQLite | Composite, partial and covering indexes can combine selection with ordered retrieval. | Usually one index per table scan, except OR optimization. Separate indexes for every flag do not automatically intersect for an AND filter. | First candidate. Lowest operational change and no second database service. |
| PostgreSQL | Combines multiple indexes using AND/OR bitmaps; B-tree composites for common filter/order paths; `pg_trgm` for substring and regex candidates. | Bitmap plans lose index ordering and may sort. Patterns without extractable trigrams scan the index. Broad exact counts still scan rows or an index. | Serious second candidate for flexible combinations, especially if SQLite needs too many composites. |
| Typesense beside the transactional database | Dedicated keyword, filter and facet APIs, including optional infix search. | Adds a second indexed copy and synchronization. Its index resides in RAM; infix needs extra memory and CPU. Search matching and facet limits need correctness checks against SQL. | Do not add by default on a small server. Trial only if a measured latency gain earns the RAM and operational cost. |
| DuckDB as an analytics sidecar | Caches data for analytical queries and supports concurrent threads inside one writer process. | Adds another dataset/version to manage; its concurrency model needs deliberate ownership. | Consider for offline aggregates or a read-only snapshot if counts dominate. No evidence yet that it improves interactive mixed filtering here. |

Sources: [SQLite planner](https://www.sqlite.org/queryplanner.html), [SQLite index choice](https://www.sqlite.org/optoverview.html#choosing_between_multiple_indexes), [PostgreSQL bitmap scans](https://www.postgresql.org/docs/current/indexes-bitmap-scans.html), [PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html#PGTRGM-INDEX), [PostgreSQL counts](https://www.postgresql.org/docs/current/functions-aggregate.html), [Typesense search/filter/facet API](https://typesense.org/docs/30.2/api/search.html), [Typesense resources](https://typesense.org/docs/guide/system-requirements.html), [Typesense infix](https://typesense.org/docs/guide/faqs.html#what-is-infix-search), [DuckDB concurrency](https://www.duckdb.org/docs/1.5/connect/concurrency).

## Make pages cheap, then measure counts separately

Test a small index portfolio against actual query plans. For example, `(name_len,name)` suits alphabetical length browsing. `(name_len,avail,name)` suits the same order when availability is fixed, but cannot generally provide name-only ordering when availability varies. Equality predicates, range predicates, null ordering and the final tie breaker all matter. Do not generate an index for every filter permutation. Cover only the columns required for the page or selected IDs; fetch rich rows after limiting results. [SQLite searching and sorting](https://www.sqlite.org/queryplanner.html#searching_and_sorting_at_the_same_time), [PostgreSQL leading index columns](https://www.postgresql.org/docs/current/indexes-multicolumn.html).

Use indexed cursor pagination over the full stable sort tuple instead of growing OFFSET. This helps fetching pages. It does not make an exact count of two million matching rows free. Cache exact counts by normalized filter plus relevant dataset versions; preaggregate common facets for each import/version. Keep the page independent of count completion. If the UI only needs to know whether more rows exist, fetch one extra row. For a capped selection, count a limited subquery rather than counting everything then taking the minimum. These are proposed changes. [SQLite scrolling windows](https://www.sqlite.org/rowvalue.html#scrolling_window_queries), [PostgreSQL count cost](https://www.postgresql.org/docs/current/functions-aggregate.html).

For substring searches, test SQLite FTS5 trigram against PostgreSQL `pg_trgm` on the domain label. SQLite MATCH does not match substrings shorter than three characters; LIKE/GLOB can fall back to scans. PostgreSQL also scans when the pattern yields no trigrams. Neither is a complete solution for `a_b__` positional filters or arbitrary one- and two-character substrings. For common fixed positions, test indexed generated columns or exact expression indexes. Short, broad patterns still have large result sets. Measure their count and ordering cost explicitly. [FTS5 trigram limits](https://www.sqlite.org/fts5.html#the_trigram_tokenizer), [pg_trgm pattern limits](https://www.postgresql.org/docs/current/pgtrgm.html#PGTRGM-INDEX), [SQLite expression index matching](https://www.sqlite.org/expridx.html).

## Stop copying the same selection for every round

Proposed model:

1. Store each pool record under a stable integer ID, with immutable import versions or an explicit source-version contract.
2. Materialize one ordered selection as compact `selection_id, position, pool_id` membership. Share it across the batch.
3. Store each reviewer's assignment as a position range or another compact membership definition. Two million names split evenly across ten reviewers means 200,000 each. It does not mean ten independent two-million-row builds. If everyone must review every name, the review workload remains twenty million exposures, but membership can still be shared.
4. Store votes/views against the assignment and selected item. Join pool display fields only for the current page. Materialize historical prices or other immutable round fields separately only where required by the existing contract.

This model removes the need to copy rich domain rows merely to open ten rounds. It still writes the shared frozen membership once, unless an immutable source version and order make a range-only selection possible. Benefits and migration cost are unmeasured. Existing names and ordered membership must remain exactly reproducible. The current implementation snapshots prices at round opening, not batch creation. Changing that timestamp, exclude-used behavior, reviewer access or overlapping assignments would change product semantics. See [existing SQL contracts](2026-10-28-performance-sql.md#contracts-for-implementation).

For random order, store `rank,name` once per reusable selection and index its positions. A finite set of precomputed shuffle orders can avoid per-request hash/sort work, but changes the arbitrary-seed contract. Preserving arbitrary seeds requires computing each new order at least once. A fixed hash plus a different starting offset is not equivalent to today's FNV shuffle. SQLite expression indexes require a matching expression and deterministic functions; an index for one fixed seed does not cover arbitrary new seeds. [SQLite expression index rules](https://www.sqlite.org/expridx.html).

## Resource and consistency rules

Keep one admitted creation worker per database, including across web processes. A durable lease or atomic database claim must enforce this; a process-local boolean is insufficient. Bound queues, chunk buffers, read concurrency, scratch space and transaction size. Give interactive reads priority over bulk creation. These are proposed operating rules, not proof of a hard latency bound.

Freeze membership from one source snapshot or immutable data version. Chunked queries against changing live data can skip, add or reorder items. SQLite WAL permits concurrent reads and a single writer, but long readers can prevent checkpoints from finishing. Close snapshots promptly. PostgreSQL Repeatable Read also provides a stable transaction snapshot, but adopting PostgreSQL does not remove the need for selection versioning. [SQLite isolation](https://www.sqlite.org/isolation.html), [WAL concurrency and checkpointing](https://www.sqlite.org/wal.html), [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

Compare engines on the server's known resource envelope using local isolation. Report cold/warm page latency, exact count/facet latency, creation phase times, peak memory, database/WAL/temp bytes, and vote latency while one creation runs. CPU affinity alone does not simulate slower storage or memory pressure. Repeat identical filter/order/seed workloads; check exact results and stable pages. Treat proposed targets such as page p95 below 100 ms and visible filter changes below 200 ms as acceptance goals, not current results. PostgreSQL work memory can multiply across plan operations and sessions, so tune a small pool and explicit memory/parallelism limits for the trial. [PostgreSQL resource accounting](https://www.postgresql.org/docs/current/runtime-config-resource.html).

Check query plans before and after each candidate index and maintain planner statistics after indexing. SQLite recommends `PRAGMA optimize` after schema changes. No production tuning is implied by this note. [SQLite statistics guidance](https://www.sqlite.org/lang_analyze.html#periodically_run_pragma_optimize).
